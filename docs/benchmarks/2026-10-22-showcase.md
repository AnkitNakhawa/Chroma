# Showcase benchmark refresh — 2026-10-22

The unchanged 18-second 1920×1080/30 showcase renders in a median **26.41 s**
with bounded graphics versus **91.20 s** with retained full-frame graphics:
**3.45× throughput**, **71.0% less wall time**. This compares Chroma with its
own reference implementation, not FFmpeg, Remotion, or another renderer.

## Method and samples

Apple M5, 16 GiB, macOS; Release build at revision
`537123200f39c0b624bef1809f6f72b66c90ca64`, developer FFmpeg encoder configuration
(not the OpenH264 release bundle). Same executable, assets, composition, media
fusion, caches and encoder settings in both modes. The frozen composition hash
is `a8faa46b091597b7952bc49799497872a2ef1ed09ff791bb8e8324e826182cb6`.

`benchmarks/bounded_graphics.py` discarded one complete encode per mode, then
alternated three fresh-process renders per mode. Each encoded all 540 video
frames and 864,000 audio sample frames, including conversion, encoding and muxing.
Asset preparation is excluded. No other Chroma test/render ran during timing;
these are local measurements with ordinary system noise, not isolated hardware
or statistical population estimates. Later equivalence verification is excluded
from benchmark timings. Raw profiles and input/executable hashes are in
[the results](2026-10-22-showcase-results.json).

| Mode | Measured wall times | Median | Throughput | Median peak RSS |
|---|---|---:|---:|---:|
| Bounded | 26.59, 25.89, 26.41 s | 26.41 s | 20.45 fps | 797.2 MiB |
| Full-frame | 90.53, 91.20, 95.67 s | 91.20 s | 5.92 fps | 745.5 MiB |

Warmups took 27.45 s and 91.02 s respectively. The optimized path remains below
real-time 1080p/30: rendering takes about 1.47× the video duration. Peak RSS does
not improve. The prior result was 3.38×; this refresh supports the same overall
conclusion, not a claim of a new optimization since that measurement.

## Quality verification

After measurement, independent persistent contexts compared every native float
RGBA buffer with `memcmp`: all 540 frames, 1,119,744,000 pixels, matched bit-for-bit.
Verification took 100.95 s and is not benchmark evidence. This run checks native
pixels; it does not introduce a new encoded-media quality comparison.

## Remaining costs

Mean leaf-stage times across the three samples (enclosing `execute`, `encode`
and `total` fields must not be added again):

| Stage | Bounded | Full-frame |
|---|---:|---:|
| Composition | 9.413 s | 74.786 s |
| Linear RGB → sRGB bytes | 9.075 s | 9.302 s |
| Decode | 2.786 s | 2.919 s |
| Decode conversion | 2.814 s | 2.938 s |
| RGB → YUV | 0.917 s | 0.940 s |
| Codec/mux | 0.638 s | 0.851 s |
| Audio | 0.307 s | 0.332 s |

Composition and output color conversion dominate the optimized path. The output
conversion calls scalar `pow()` per channel per pixel. Decode still materializes
RGBA8 and linear float surfaces, and encoding reads a full float surface and
writes RGB24 before YUV conversion. Merely accelerating the codec cannot remove
most of the current cost.

## Next experiments

1. Optimize linear-float → sRGB8 conversion. Benchmark SIMD or an exact
   quantization-boundary method against the scalar oracle. A naive approximate
   lookup table can change rounded bytes; preserve pixel/video quality gates.
   Halving this stage alone would predict roughly 21.9 s total if other costs
   stay fixed, still slower than real time. This is an estimate, not a measurement.
2. Profile and reduce remaining full-canvas clears, solid blending and temporary
   surfaces; consider safe opaque replacement and reusable scratch storage.
   Measure each change independently against this frozen corpus.
3. Evaluate bounded worker parallelism for independent pixel rows/tiles and
   conversion, then decode/render/encode overlap. Preserve blend ordering,
   cancellation and bounded memory; do not enqueue an unlimited frame pipeline.
4. Design a GPU-resident media/color/composition path. CUDA/NVDEC/NVENC requires
   NVIDIA hardware; this Apple host would require Metal and Apple media APIs.
   Account for CPU/GPU transfers and text upload costs before claiming a speedup.

## GPU implementation status

There are no CUDA or Metal render kernels, hardware-frame rendering pipeline, or
GPU encoder selection implemented. `chroma hardware` is capability discovery;
`gpu_fusible` is planner metadata. The current probe reports
`pipeline_implemented: false`. All timings above use CPU rendering. Availability
of an FFmpeg device type does not mean Chroma uses that device.
